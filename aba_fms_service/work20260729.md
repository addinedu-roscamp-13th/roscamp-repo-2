## 2. 직접 주차 — 안전가드 제거와 그 뒤의 삽질 (기록용)

`ex ±0.75` 밖이면 `throw` 하던 가드를 제거하는 과정에서 **연달아 두 번 잘못된 수정**을 했다.
같은 실수를 반복하지 않기 위해 원인과 근거를 남긴다.

### 2-1. HTTP 422
`steer_ex_tol 0.99` / `align_ex_tol 0.995` 를 보냈는데 로봇 `ParkConfig` 의 pydantic 상한이
`le=0.9` / `le=0.98` 이었다. → 상한 안으로 되돌리고 코드에 주석으로 명시.
덤으로 **FastAPI 422 의 `detail` 은 문자열이 아니라 배열**이라 기존 에러 핸들러가 통째로
버리고 있었다 → `필드명: 사유` 로 표시하도록 2곳 수정.

### 2-2. 판단 기준을 `ex` 로 잡은 것이 틀렸다
이 카메라는 `fx=471 / 480px` → 수평 반화각 `atan(240/471) ≈ 27°` 로 좁아 **`ex` 가 금방 포화**된다.
실측: 물리적으로 **19°** 밖에 안 틀어진 마커가 `ex -0.81`(프레임 왼쪽 끝)로 찍혔다.
`ex` 만 보고 제자리 회전을 걸었더니 바로 앞 마커를 두고 헛돌았다(yaw 9.9°→33.9°, 마커 80회 로스트).
→ 파일에 이미 있던 `markerBearingDeg()`(pose `atan2`, 없으면 fx 환산)를 쓰도록 변경.

### 2-3. `steer_ang_max` 를 올린 것이 곡선 접근을 피벗으로 바꿨다
로봇 메인 PID(`aruco_dock_robot.py:965`)는 `_vel_to_speeds(linear, angular)` 를 그대로 쓴다.
`angular > linear` 면 한쪽 바퀴가 역회전 → 제자리 회전.
실측 `linear 0.045 / angular -0.08 → left +22, right -5`.
원래 주석에 `steer_ang_max: 0.05 // 조향을 전진보다 작게` 경고가 있었는데 그걸 깼다.

### 2-4. 그래서 낮췄더니 이번엔 아예 안 움직였다 ★ 이게 핵심
`driving.py:148`
```python
left  = int((lin - ang) * MAX_SPEED)   # MAX_SPEED = 75
right = int((lin + ang) * MAX_SPEED)
```
`aruco_dock.py:61 _scale_min_drive` 는 **peak 만** `min_drive` 로 끌어올린다.
안쪽 바퀴 비율 `r = (lin−|ang|)/(lin+|ang|)` 는 그대로 남으므로 **안쪽 = min_drive × r**.

실측 `lin 0.045 / ang 0.03 → r = 0.2 → L=32, R=6` → **12초간 완전 정지**
(카메라로 확인: `cx 180.0→179.8`, `z 0.797→0.799`, `side 29.7` 고정. 모터 데몬 pid 2897 은 정상).

**이 구동계의 근본 제약: 바퀴 하나라도 PWM 약 32 밑이면 로봇이 안 움직인다.**
(`aruco_dock.py:52 _MIN_DRIVE = 32` 가 코드가 스스로 선언한 값이고, `±26` 피벗도 20초 무반응)
→ **저속 곡선 주행이 물리적으로 불가능**하다. 안쪽 바퀴를 살리려면 `|ang| ≤ lin/7` 이고,
그때 곡률은 `κ ≈ 0.14 rad/m` — 0.8m 가는 동안 **6.5° 밖에 못 꺾는다.**

이 사실 때문에 3번의 '회전 → 직진' 방식으로 갈아탔다.

## 3. pose(6-DOF) 기하 주차 — POSE DOCK (본 작업의 결론)

### 왜 ex 제어로는 안 되나
`ex` 는 "마커가 화면 어디에 있나"만 알려줄 뿐 **"마커가 어느 쪽을 보고 있나"를 모른다.**
실측 결정적 사례:
```
ex = -0.015  → 이미지상 완벽히 정면
yaw = +19.0°, 법선 n = (+0.341, -0.930)
axis_lat = x·nz − z·nx = -0.262 m
```
**마커는 정면에 보이는데 로봇은 마커 정면축에서 26cm 옆으로 벗어나 있었다.**
`ex` 만 보고 직진하면 19° 비뚤어진 채로 처박는다. 게인을 아무리 만져도 안 됐던 근본 이유.

### 수학 (일반식 — 현재 자세에 맞춘 튜닝이 아니다)
solvePnP 가 주는 `x, z, yaw, nx, nz` 로 직접 푼다.
```
range    = hypot(x, z)                        마커까지 거리
axis_lat = x·nz − z·nx                        마커 정면축에서 옆으로 벗어난 거리
d_hold   = clamp(range − target, 0, standoff)
W        = (x + nx·d_hold, z + nz·d_hold)     마커 정면축 위 진입 경유점
θ        = atan2(W.x, W.z)                    경유점 방위각 (+ = 오른쪽)
```

⚠️ **거리는 반드시 `range = hypot(x,z)` 를 써야 한다. `z`(전방 성분)를 쓰면 안 된다.**
`z` 는 로봇이 제자리 회전만 해도 값이 변해(물리 거리는 그대로인데) 경유점 W 가 따라 움직이고,
`turn -22° → +12° → -6°` 처럼 좌우로 진동한다. 시뮬레이션에서 잡은 실제 버그.

### 실행 — '제자리 회전 → 직진' 프리미티브만 사용
2-4의 제약(저속 곡선 불가) 때문에 곡선 제어를 버리고 다음만 쓴다.
- `POST /api/robot/rotate {angle, speed}` — angle 음수 = 우회전
- `POST /api/robot/move {direction:"forward", distance, speed}`

둘 다 **블로킹**(완료 후 `status:"done"`)이고 **양 바퀴를 대칭으로 구동**해 항상 정지마찰을 넘긴다.
단 로봇 드라이버(`drivers/driving_driver.py:57,86`)는 **시간 기반 개루프**
(`duration = 거리 / 가정속도`, `linear = speed×0.25 m/s`, `angular = speed×1.0 rad/s`)라
오차가 쌓인다 → **한 스텝을 짧게 끊고 매번 pose 를 다시 재서 재계획**(플래너 레벨 폐루프).

### 화각 제한 + 마커 기억 복구
카메라 수평 반화각이 27° 뿐이라 회전/직진 중 마커가 화각 밖으로 나간다(제한 전 143/196 = 73%).
- **회전 제한** `keepInViewDeg = 20` — 회전 후 방위각이 ±20° 안에 남도록 회전량을 자른다
- **직진 제한** `keepMoveDeg = 26` — `d ≤ z − |x|/tan(26°)`. 단 `minLegM` 은 항상 보장
  (전진을 아예 못 해 못 붙는 것보다, 놓치고 복구하는 편이 낫다)
- **기억 복구** — 마지막으로 본 방위각과 그 뒤 명령한 회전량의 합을 들고 있다가
  놓치면 `추정 방위각 = 마지막 방위각 − 그 뒤 회전량` 만큼 되돌리고, 안 되면 ±15°씩 훑는다
  (`lostRetries = 3`). `parkp_robot.py` 의 메모리 큐와 같은 아이디어.

채택: **회전 20° / 직진 26°** → 수렴 100%, 최종 `range 0.200m / 축이탈 ≤0.048m / 방위 ≈0°`.

## 5. 실주행에서 나온 문제들 (전부 로봇 `parkp` 수정 + 재배포)

실제로 돌려 보니 시뮬레이션에서 안 보이던 것들이 연달아 나왔다. 순서대로 기록한다.

### 5-1. 시작하자마자 "벽/IR 센서 안전 정지" — IR 오용
```python
ir_hit = bool(ir and (ir.get("left") or ir.get("center") or ir.get("right")))
```
`_read_ir()` 는 `{left, center, right}` **아날로그 원값**만 준다(`obstacle` 필드 자체가 없음).
실측 `236 / 300 / 237` → `bool(236)` = True → **매 루프 무조건 안전 정지**.
IR 은 바닥을 보는 **테이프 센서**라 장애물 감지가 애초에 불가능하다.
→ `ir.get("obstacle")` 이 있을 때만 반응하도록 바꾸고 `stop_on_ir` 기본값을 **False** 로.
   장애물 판정은 초음파(`_read_dist`)만 신뢰한다.

### 5-2. 좌우로 폭주 — 회전이 항상 최대 속도
`min_drive` 를 정지마찰 위(45)로 올린 대가로 **최저 속도 = 최고 속도**가 됐다.
`recall` 중 `L=-45 R=45` 가 쉬지 않고 나가 미세 조정이 불가능했다.
→ 제자리 회전을 **펄스(돌고-멈춤)** 로. `turn_pulse_s 0.16 / turn_pause_s 0.34` (듀티 32%).
   순간 PWM 은 stall 위를 유지하고 평균 각속도만 1/3 로 낮춘다.
   (기존 `aruco_dock` · `park_dock` 이 쓰는 방식과 동일)

### 5-3. 근접하면 마커를 못 보는데 계속 찾음
카메라가 위를 향해 있어 마커에 가까워지면 화각 **아래로** 빠진다. 정상 현상인데 '분실'로 보고
복구 회전을 걸어 다 온 로봇이 제자리에서 헤맸다.
→ `near_done_m = 0.32` 추가. **마지막으로 본 거리가 32cm 이내면 분실이 아니라 '도착'** 으로 처리.

### 5-4. "odom/메모리가 없어 복구 불가 — 중단" ★
`memory_len = 35` 로 기억은 쌓였는데 **전부 `gx=None`** 이었다.
`gx`(전역 좌표)는 `_to_global()` 이 만드는데 `_odom()` 이 필요하고,
로봇의 `ros_bridge.get_topic("odom")` · `"tf_pose"` 가 비어 있었다 → 복구 재료 0개 → 즉시 중단.

**도킹 복구가 ROS 스택 건강 상태에 의존하는 게 설계 오류다.** nav2 가 흔들리면 주차가 통째로 죽는다.
→ **카메라 전용 복구** 추가. 마커는 마지막으로 보이던 '쪽'으로 프레임을 벗어나므로 부호만 있으면 된다.
```
last_bearing 부호 → 그 방향으로 펄스 회전 탐색
recall_sweep_s(2.5s) 안에 못 찾으면 → 반대 방향으로 더 넓게
recall_timeout_s(12s) 까지 반복
```
odom 이 살아 있으면 기존 전역좌표 복구를 그대로 쓰고, 없을 때만 이 경로로 빠진다.
상태: `[recall_cam] 마커 분실 — 마지막으로 본 쪽(우)으로 펄스 회전 탐색 중 (3/12s)`

### 5-5. 잘 도착했는데 "초음파 안전 정지" 로 표시
`target_wall_cm` 은 이름 그대로 **목표 벽 거리**지 위험 임계값이 아니다. 도달 = 성공이다.
5-1 을 고치면서 IR 장애물과 한 덩어리(`safety_stop`)로 묶은 게 잘못이었다.
→ 정지 사유를 셋으로 분리:

| 조건 | phase | 메시지 |
|---|---|---|
| 마커 기준 거리·방위 도달 | `done` | `주차 완료 — 마커 정면 0.34m (벽 8.0cm)` |
| 벽 목표거리 도달 | `done` | `주차 완료 — 벽 3.0cm 정위치 도달` |
| 실제 장애물 신호 | `safety_stop` | `장애물 감지 — 안전 정지` |

### 5-6. UI 설정값이 로봇까지 안 감
`startParkP()` 가 `marker_id / dictionary / marker_len_m / target_distance_m / standoff_m` 만 보내서
나머지는 전부 로봇 기본값이 쓰였다. 화면에 벽 3cm 로 해 놓고 **8cm(로봇 기본값)에서 섰다.**
→ UI 숫자 입력을 전부 연결:

| UI 항목 | 전달 필드 |
|---|---|
| 벽 정지거리(cm) | `target_wall_cm` (+ `slow_wall_cm = 정지거리 + 8`) |
| 전진/후진 상한 | `lin_max` |
| 전면/후면 목표 | `target_size` (미캘리브레이션 대체 제어용) |

로봇 제약(`target_wall_cm` 3~80, `lin_max` 0.02~1.0, `target_size` 0.05~0.95)에 맞춰 클램프.

⚠️ 입력 하한이 `min={2}` 인데 `parkp` 제약은 3 이상이라 2 입력 시 실제로는 3 으로 동작한다.
   입력 하한을 3 으로 올리지 **않은** 이유: 2cm 를 쓰는 라인 주차(`startLineDock` 의
   `Math.max(2, wallTargetCm)`)가 같이 묶여버린다. parkp 로 보낼 때만 클램프하는 편이 부작용이 없다.

⚠️ `wallTargetCm` 등은 **컴포넌트 state 라 새로고침하면 기본값으로 돌아간다**(저장 안 함).
   전역 설정으로 유지하려면 `FleetCoordinatorSettings` 같은 싱글턴 설정 테이블 패턴을 쓰면 된다
   (`create_all` 이 기동 시 멱등 실행되므로 모델만 추가하면 테이블은 자동 생성).

`아주 잘 왔어` — 축이탈 8cm / 벽 목표거리 도달로 주차 성공 확인.
