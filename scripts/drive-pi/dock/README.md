# 주차 단계별 디버깅

**처음 맞출 때만 쓴다.** 운영에서 주차는 BT 가 한다 (`RETURNING` → `/fleet_cmd{dock}`).

```
./1-line.sh      1. 테이프가 보이나       (로봇 안 움직임)
./2-rotate.sh    2. 주차장 방향 회전만
./3-approach.sh  3. 벽까지 직선 접근만
./search.sh         테이프를 놓쳤을 때 다시 찾기
./status.sh         지금 어디까지 갔나    (로봇 안 움직임)

../dock.sh          전체를 한 번에
../dock.sh stop     즉시 중단
```

---

## ⚠️ 먼저 알아야 할 것 — 주차는 **라인 트레이싱**이다

저장소에 도킹 구현이 **셋** 있는데 서로 다르고, 이름 때문에 오해하기 쉽다.

| 모듈 | 엔드포인트 | 방식 | 지금 누가 부르나 |
|---|---|---|---|
| `line_dock` | `/line/*` | 바닥 테이프 + IR 추종, 초음파로 정지 | `park_dock` 이 위임 |
| `park_dock` | `/park/*` | 진입각 정렬 → 테이프 탐색 → **`line_dock` 위임** → 벽 정지 | **BT** (`dock_runner`) |
| `aruco_dock` | `/dock/*` | 아르코 마커 PID 접근 (완결형, 별개 구현) | **관제 화면 수동 버튼만** |

BT 가 부르는 경로를 끝까지 따라가면:

```
BT → /fleet_cmd{dock} → dock_runner → park_dock._park_loop
                                        ├ _rotate_to_odom    TF yaw 180°   ← 카메라 안 씀
                                        ├ _search_line        IR
                                        ├ _line_loop          IR 12 Hz     ← 본체
                                        └ 벽 정지             초음파
```

**아르코는 이 경로에 없다.** `park_dock` 이 아르코를 쓸 수 있는 자리는 진입각 정렬
(`rotate_ref: "marker"`) 하나뿐이고, 그것도 **각도 센서로만** 쓴다 — 도킹 컨트롤러는
여전히 라인이다. 게다가 `dock_runner` 가 `rotate_ref: "odom"` 을 주므로 **그마저도 안 탄다.**

그래서 지금 주차의 CPU 부하는 **IR·초음파 폴링 12 Hz** 가 전부다. 카메라 비전은 안 돈다.

### 작성자가 의도한 것 (코드에 남아 있는 근거)

`line_dock_robot.py` 머리말 (2026-07-07):

> **배경: 아르코 마커만으로는 최종 주차 정밀도가 부족 → 주차 스팟 바닥에 붙인
> 흰 테이프를 카메라로 추종해 마지막 구간을 미세조정한다.**

그러니까 **둘 중 하나를 고르는 게 아니었다.** 아르코가 먼저 있었고, 정밀도가 모자라서
라인 추종을 **마지막 단계로 덧붙인** 것이다:

```
의도   아르코 접근(마커 호밍 · 축 정렬 · 근접 정렬)  →  라인 미세조정  →  벽 정지
```

`aruco_dock` 이 하는 일도 그 머리말과 FMS README 에 상세히 적혀 있다 — 전진 펄스 +
마커 중심 호밍, 캘리브레이션 pose 로 축 이탈 보정, 근접 사전 정렬, 초음파 벽 정지.
버리려고 만든 코드가 아니다.

---

## ❓ 작성자에게 물어볼 것 두 가지

의도는 위와 같은데, **지금 배선은 그렇게 안 돌아간다.** 아래 둘은 코드를 읽어서 확인한
사실이고, 어느 쪽이 맞는지는 **실물에서 돌려 본 사람만 안다.**

### ① BT 가 아르코 접근 단계를 건너뛴다

```
의도       아르코 접근  →  라인 미세조정  →  벽 정지
현재 BT    TF yaw 회전  →  라인 미세조정  →  벽 정지
              └─ 아르코 단계가 통째로 없다
```

`dock_runner.park_config()` 가 `rotate_ref: "odom"` 을 준다. 그러면 `_park_loop` 은
`_rotate_to_marker` 대신 `_rotate_to_odom` 을 타고, 마커는 한 번도 안 본다.

> **물어볼 것**: 아르코 접근을 빼고 라인만으로 충분하던가? 아니면 배선이 빠진 건가?
> 전자면 `aruco_dock` 은 관제 수동 버튼 전용으로 남기고, 후자면 `dock_runner` 의
> 기본값을 `marker` 로 바꿔야 한다 (`park_dock` 에 이미 그 경로가 있다).

### ② 라인 검출이 카메라가 아니라 IR 이다

머리말은 **카메라 ROI 이진화 무게중심**이라고 적어 놨다:

> 화면 하단 ROI → 그레이스케일 → 이진화 → 상/하 2개 밴드의 흰 픽셀 무게중심으로
> 좌우 오프셋과 라인 기울기를 계산

그런데 `line_dock._line_loop` 은 그 함수들을 **한 번도 부르지 않는다:**

```
정의된 곳    line_dock.py:188  _grab_frame()
             line_dock.py:196  _detect_line()
호출하는 곳  없음

실제 루프    _read_ir()  +  _read_wall_cm()   12 Hz
```

> **물어볼 것**: IR 이 더 잘 돼서 갈아탄 건가, 아니면 카메라 경로가 미완성인가?
> 전자면 `_grab_frame`/`_detect_line` 은 죽은 코드라 지워야 하고, 머리말도 고쳐야 한다.
> 후자면 왜 안 불리는지 찾아야 한다.

### ③ `park_dock` 이 아르코 접근을 조합하지 않는다 — **가장 큰 격차**

머리말의 "아르코 접근 → 라인 미세조정" 에서 **앞부분이 `park_dock` 에 아예 없다.**

`park_dock` 이 `aruco_dock` 에서 가져다 쓰는 건 셋뿐이다:

```python
from app.routers.aruco_dock import _MIN_DRIVE     # 로봇별 최소 구동값(캘리브레이션)
from app.routers.aruco_dock import _STEER_SIGN    # 조향 부호
aruco_dock._detect(...)                           # 마커 검출 — **각도 센서로만**
```

`_rotate_to_marker` 는 이름 그대로 **마커가 화면 중앙에 오도록 제자리 회전**만 한다.
전진하지 않는다.

진짜 아르코 접근은 `aruco_dock._dock_loop` 이고 — 전진 펄스 + 마커 중심 호밍,
캘리브레이션 pose 로 축이탈 보정, 근접 사전 정렬, 초음파 벽 정지 — **`park_dock` 은
이걸 한 번도 부르지 않는다.** 호출하는 곳은 `/dock/start`(관제 수동 버튼)뿐이다.

```
머리말 의도   아르코 접근(호밍·축정렬·근접정렬)  →  라인 미세조정  →  벽 정지
park_dock     제자리 회전만                      →  라인          →  벽 정지
현재 BT       TF yaw 회전 (마커도 안 봄)         →  라인          →  벽 정지
```

> **물어볼 것**: `park_dock` 이 `_dock_loop` 을 안 부르는 게 의도인가?
> - **의도라면** — 아르코는 관제 수동 전용이고, 자동 주차는 "회전 + 라인"이 전부다.
>   그러면 머리말의 "아르코 접근 → 라인 미세조정"은 **사람이 관제에서 아르코를 돌린 뒤
>   라인을 돌리는 2단계 수동 절차**를 뜻한 것일 수 있다.
> - **아니라면** — `park_dock` 에 아르코 접근 단계가 통째로 빠져 있다.
>
> ⚠️ 그래서 `DOCK_MARKER_ID` 를 줘도 **아르코 접근은 안 일어난다.** 진입각만 마커로 잡는다.

### ④ `action: "dock"` 을 아무도 안 보낸다

`fleet_link._dispatch` 에 `dock` 처리를 넣어 `dock_runner` 로 잇긴 했는데,
**그 액션을 보내는 곳이 저장소에 없다.** BT 의 복귀 드라이버는 `home` 을 보낸다:

```python
"return_dock": FleetCmdDriver(self, "home")        # libi_modes/main.py
```

`home` → `mission.go_home()` → 로봇에 `HOME` 이 등록돼 있으면 거기로, 없으면 맵 원점.
**즉 지금 복귀는 정밀 주차를 아예 안 거치고 nav2 로 한 점을 찍고 끝난다.**

**이 답에 따라 CPU 도 달라진다.** 지금은 IR·초음파 폴링 12 Hz 뿐이라 거의 안 먹는데,
카메라 경로가 살아나면 매 프레임 OpenCV 가 돌아 얘기가 완전히 달라진다.

## 왜 쪼개 놨나

전체를 한 번에 돌리면 **어디서 왜 틀어졌는지 알 수가 없다.** 테이프를 못 보는 것,
회전 각도가 안 맞는 것, 벽 거리를 잘못 재는 것은 원인도 고치는 법도 전부 다르다.
`1-line` 에서 테이프가 안 잡히면 뒤 두 단계는 볼 필요조차 없다.

## 조절할 값

환경변수로 준다. 스크립트를 고치지 않는다.

| 변수 | 기본 | 언제 바꾸나 |
|---|---|---|
| `DOCK_APPROACH_YAW_DEG` | `180` | 진입각이 안 맞을 때 |
| `DOCK_ROTATE_REF` | `odom` | 진입각을 TF yaw 대신 마커로 잡고 싶을 때 (`marker`) |
| `DOCK_MARKER_ID` | (없음) | 주면 자동으로 `marker` 기준이 된다 |
| `DOCK_MARKER_DICT` | `DICT_4X4_50` | 다른 아루코 사전을 쓸 때 |
| `ROBOT_AGENT_HOST/PORT` | `127.0.0.1:9001` | 노트북에서 로봇을 원격으로 부를 때 |

```bash
DOCK_APPROACH_YAW_DEG=175 ./2-rotate.sh
DOCK_MARKER_ID=7 ./2-rotate.sh          # 진입각만 마커로
```

## 진입각이 180°인 이유

```
입구   ( 0.581, -0.033)
주차장 (-0.001, -0.033)     y 가 같다 → 180°(-x) 방향으로 0.582 m 직선
```

⚠️ `waypoint.yaml` 의 `입구` yaw 는 **90°** 다. 그 자세로 도착하면 주차장이 아니라 옆을
본다. 그래서 **주차가 자기가 회전한다.** 정점 yaw 를 180 으로 바꾸지 않는 이유: 입구는
주차 말고 다른 주행도 지나는 길목이라, 거기서 항상 주차장을 보게 만들면 그 주행들이
엉뚱해진다.

## 전제

`robot_agent`(FastAPI) 서버가 떠 있어야 한다. **`pi.sh` 는 안 띄운다** — ROS 스레드
두 개(`fleet_link`·`ros_bridge`)만 띄운다.

```bash
cd ~/controller/drive/robot_agent && pm2 start ecosystem.config.js
```

BT 경로(`/fleet_cmd{dock}`)는 서버 없이도 된다 — `fleet_link` 이 같은 프로세스에서
`dock_runner` 를 부르기 때문이다. 그쪽이 **실제로 도는 길**이므로, 주차가 한 번
맞고 나면 검증은 BT 경로로 하는 게 낫다.

## ⚠️ 실물 미검증

이 절차는 IR·초음파·모터가 필요해 sim 에서 돌릴 수 없고, 작성 시점에 실물 접근이
없었다. **아직 한 번도 돌려보지 못했다.** 처음 돌릴 때는 위 순서대로 하나씩 볼 것.
